# 規範改善回饋機制（Policy Feedback Loop）

## 目的與觸發
每輪實際開發、修復、部署、審查、阻塞或回顧後，在交付報告記錄一次規範回寫評估。目標是避免同類問題在其他專案重複發生；**評估不等於自動改寫另一個儲存庫**。若只是同步此規範本身，不再遞迴產生相同提案。

## 執行步驟
1. 從本輪回顧提取已證實的根因、處置、風險、驗證證據及可重用建議；未證實標 UNKNOWN，不強推規範。
2. 查閱當前專案與目標儲存庫的 `AGENTS.md`、既有 Issue／PR／規範，判斷是否已有相同保護；已涵蓋記 `NO_CHANGE`，不得再建重複 Issue。
3. 分離通用原則與特定技術操作：跨專案共用流程進 `agent-development-loop`；新專案預設契約進 `agent-project-template`；雲服務、帳號、資料表或技術細節仍留原專案。
4. 按以下結果分類，記入 retrospective 與交付回報：
   - `LOCAL_ONLY`：只適用目前專案。
   - `LOOP_CANDIDATE`：建議改善共用執行流程。
   - `TEMPLATE_CANDIDATE`：建議改善新專案預設契約。
   - `BOTH_CANDIDATE`：兩者皆需評估，且避免重複撰寫規範。
   - `NO_CHANGE`：無新規則必要或已涵蓋。
   - `DEFERRED`：證據不足、權限不足或待獨立驗證。
5. 候選需記錄來源 Issue／PR（若安全可公開）、去識別化問題描述、現有規範比對、預期效果、風險、受影響 repo、建議文件及驗證方法。先比對是否有開放中的相同提案，再決定是否建 Issue。
6. 跨 repository 寫入、開 PR、合併或部署，必須分別符合各 repo 的授權和安全 Gate；不可因本節擴權。涉及安全／隱私的修訂需獨立審查、測試規範連結／關鍵條款保留，證據不足維持待審。
7. 回寫追蹤使用 `PROPOSED → REVIEWED → ADOPTED / REJECTED / DEFERRED`；在來源 retrospective 記目標 repo 與 Issue／PR，避免重複提案。僅僅 `ADOPTED` 不代表其他既有專案已自動套用。

## 安全與防循環
公開內容一律經 PII_SCAN 與人工必要確認，不輸出真實姓名、員編、識別符、帳務關聯、token、秘密或私密環境資訊；避免在 diff 中再次曝露舊值。不得降低 fail-closed、測試、權限或正式部署條件。共用文件只有原則和入口；實作細節保留單一權威來源，避免互相矛盾。未發現適合回寫內容時只記 `NO_CHANGE`，**不阻塞正常交付**。

## 每輪輸出格式
`規範回寫評估：<分類>｜證據：<安全摘要或內部連結>｜目標：<repo/文件或無>｜追蹤：<Issue/PR 或無>｜狀態：<狀態>`
