# Guarded canonical identity repair

`scripts/lib/canonical-identity-repair.mjs` plans the approved repair for one identity split with exactly two duplicate active orders on 2026-10-06 and 2026-10-07, each totaling 100. It does not discover identities or decide which orders to keep. The caller must supply a freshly read, reviewed snapshot and the approved repair identifiers. Production user, employee, LINE, order, ledger, and database identifiers belong in a private operator input file only; never commit them or place them in fixtures or this runbook.

## Required frozen input

The planner requires both identities, the transferred LINE profile, the maintenance Admin actor, and the exact timestamp and new audit, refund, and order-history identifiers. Supply the source and canonical profile fields and `updated_at` values; both balance mirrors; canonical ledger row count, latest balance and sequence; source latest sequence; and the global latest sequence. `preservedOrders` must name the two canonical active orders and each original ORDER debit's transaction ID, sequence, and `balance_after`. `refunds` must name each source active order and its original ORDER debit ID, sequence, and `balance_after`, along with fresh refund and transition IDs. `guestSessionIds` must enumerate every unrevoked session attached to the source user or its employee ID, including provisional sessions whose `user_id` is null. Freeze the operator's role, active state, identity snapshots, verification status, and `updated_at` as well.

The repair is bounded to the exact incident shape: the source is an active normal User with a misbound employee ID and LINE ID, exactly two total orders and two source ledger rows, the two active 100-unit orders and their -100 debits, source balance -200, no source opening-balance snapshot, and no in-progress source idempotency request. The canonical account must remain active, retain its employee ID, balance, ledger history, and the two active orders. The planner fails closed when the live state differs.

## Apply

1. Read the formal migration version and confirm the current D1 target. Read the two users, their orders, relevant ledger rows joined to `balance_ledger_sequence`, guest sessions, opening-balance snapshots, idempotency state, operator row, and foreign-key check. Review exact candidate ownership and obtain explicit approval for each order to cancel and refund. Keep the frozen input and query output outside the repository.
2. Build a plan with `buildCanonicalIdentityRepairPlan(input)`. Bind every `{sql, params}` with the active Worker D1 binding: `env.DB.prepare(sql).bind(...params)`. Apply the complete statement list in one `env.DB.batch(statements)` call. The planner places several bounded precondition assertions first, before any mutation. Each relies on the formal `employee_guest_sessions.token_hash NOT NULL` constraint to abort the batch when its frozen checks are stale; verify that constraint exists before use. Do not split the assertions and writes across calls.
3. If the batch response is ambiguous, stop and run the read-only postcondition and before/after reconciliation before considering any retry. A repeated repair is a no-op only after `buildCanonicalIdentityRepairPostconditionQuery(input)` returns `is_applied = 1`. A caller-supplied state flag is not proof.
4. After a successful batch, require the postcondition to return `is_applied = 1`. Compare all pre-existing canonical and source ORDER ledger rows, sequence numbers, all canonical orders, and source historical order snapshots byte-for-byte. Confirm only the approved source orders transitioned to CANCELLED; there are two REFUND rows of +100 with balances -100 then 0; source mirror is 0 and source account is inactive with its employee ID reserved and LINE binding cleared; canonical identity owns the LINE ID and approved display name while canonical balance and ledger remain unchanged; every frozen source guest session is revoked; the audit row records both identities, retained/cancelled orders, refund transactions, and balance evidence; and `PRAGMA foreign_key_check` is empty. Likes and completed idempotency history remain attached to their original owner.

The planner appends refunds to the source ledger and relies on the formal sequence trigger. It does not rewrite old orders, old ledger rows, or their sequence assignments, transfer historical ledger ownership, merge arbitrary balances, or rekey foreign-key history. Do not use the Cloudflare REST query batch endpoint as an atomic transaction unless its rollback semantics have been independently established; this repair requires the Worker D1 `batch()` transaction contract.
